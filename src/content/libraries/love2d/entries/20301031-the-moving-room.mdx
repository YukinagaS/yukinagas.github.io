Build a 240×160 virtual room containing a controllable rectangle. Movement
should remain the same speed regardless of frame rate, and a small debug readout
should show the current position, speed, and frame time.

---

### Learning goals

- Develop a precise model of what LÖVE calls once and what it calls every frame.
- Separate changes to game state from drawing that state.
- Use `dt` to express movement in units per second rather than units per frame.
- Work with screen coordinates, where positive x points right and positive y
  points down.
- Treat debug drawing as a normal development tool.

### State, update, and draw

The most useful initial model for a LÖVE game is: **state exists continuously;
update changes it; draw presents it.** `love.load` establishes the initial state
and loads resources. LÖVE then repeatedly calls `love.update(dt)` and
`love.draw()`.

Moving a fixed number of pixels per frame makes the apparent speed depend on
the frame rate. Instead, define speed in pixels per second. If the previous
frame took `dt` seconds, movement during the current update is `speed * dt`.

```lua
local player = { x = 100, y = 70, speed = 90 }

function love.update(dt)
    if love.keyboard.isDown("right") then
        player.x = player.x + player.speed * dt
    end
end

function love.draw()
    love.graphics.rectangle("fill", player.x, player.y, 12, 12)
end
```

Variables declared outside the callbacks persist between frames. Recreating
the position inside `love.update` would reset it during every update. Keep the
simulation position as a floating-point value and round only the drawn position
if the visual style requires pixel alignment.

### A complete moving room

Create a project folder with this `main.lua`. The logical room remains 240×160
even though it is displayed at three times that size.

```lua
local room = { w = 240, h = 160, scale = 3 }
local player = {
    x = 100,
    y = 70,
    w = 12,
    h = 12,
    speed = 90,
}
local frameTime = 0

function love.load()
    love.window.setMode(
        room.w * room.scale,
        room.h * room.scale
    )
    love.window.setTitle("The Moving Room")
    love.graphics.setBackgroundColor(0.08, 0.10, 0.14)
end

function love.update(dt)
    frameTime = dt

    local dx, dy = 0, 0

    if love.keyboard.isDown("right", "d") then
        dx = dx + 1
    end
    if love.keyboard.isDown("left", "a") then
        dx = dx - 1
    end
    if love.keyboard.isDown("down", "s") then
        dy = dy + 1
    end
    if love.keyboard.isDown("up", "w") then
        dy = dy - 1
    end

    local length = math.sqrt(dx * dx + dy * dy)
    if length > 0 then
        dx, dy = dx / length, dy / length
    end

    player.x = math.max(
        0,
        math.min(
            room.w - player.w,
            player.x + dx * player.speed * dt
        )
    )
    player.y = math.max(
        0,
        math.min(
            room.h - player.h,
            player.y + dy * player.speed * dt
        )
    )
end

function love.draw()
    love.graphics.push("all")
    love.graphics.scale(room.scale)
    love.graphics.setColor(0.4, 0.85, 1)
    love.graphics.rectangle(
        "fill",
        player.x,
        player.y,
        player.w,
        player.h
    )
    love.graphics.pop()

    love.graphics.setColor(1, 1, 1)
    love.graphics.print(
        string.format(
            "x %.1f  y %.1f  speed %d  dt %.4f",
            player.x,
            player.y,
            player.speed,
            frameTime
        ),
        12,
        12
    )
end
```

### Why the details matter

The vector `(1, 1)` has a length of √2. Normalizing a non-zero input vector
makes diagonal movement cover the same distance as horizontal movement. Never
divide the zero vector because it has no direction.

The bounds subtract the player width and height. Otherwise, only the player’s
origin would stop at the room edge while the remainder of the rectangle moved
outside it. Multiplying by `dt` stabilizes ordinary movement, but it does not
prevent a very fast object from crossing a wall during one long frame; collision
handling addresses that separately.

### Build sequence

1. Create the window and choose a background color.
2. Define a player table containing position, dimensions, and speed.
3. Read held directional input in `love.update`.
4. Multiply the intended movement by `dt`.
5. Normalize non-zero diagonal input.
6. Clamp the player to the logical room.
7. Draw the player and a debug readout.

### Verify the result

- Hold opposite directions together and confirm that movement on that axis
  cancels.
- Travel diagonally and horizontally for the same duration and compare the
  distances.
- Reach all four edges without clipping.
- Explain why drawing at 3× scale does not multiply the stored speed.
